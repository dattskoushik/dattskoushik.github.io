TinyETL: Idempotent Data Framework

A lightweight, configuration-driven ETL framework designed for robust data processing with built-in retry mechanics and data quality checks.

Problem

Small to medium pipelines often rely on ad-hoc scripts that fail silently, lack retry logic, and pollute target tables with partial data writes.

Architecture & Data Flow

[Source API/CSV] -> (Ingestion Task) -> [Raw Storage]
       -> (Transformation & Validation) -> [Staging Area]
       -> (Atomic Upsert) -> [Target PostgreSQL Warehouse]

Engineering Decisions

  • Idempotency: Implemented transaction-based upserts so failed jobs can be safely re-run without duplicating data.
  • Data Quality: Enforced schema validation and null-checks before writing to the target warehouse.
  • Simplicity: Avoided heavy orchestration tools like Airflow for scale-appropriate workloads, favoring a cron-friendly execution model.

[ Python ] [ Distributed Systems ] [ Redis ]

Raft-Based Distributed KV Store

A highly available distributed key-value store implementing the Raft consensus algorithm for fault-tolerant state machine replication.

Problem

Single-node databases represent single points of failure. Replicating state reliably across a cluster of nodes requires handling network partitions and node crashes.

Architecture & Data Flow

Client -> [Leader Node (gRPC)] -> (AppendEntries RPC) -> [Follower 1]
                               -> (AppendEntries RPC) -> [Follower 2]
       <- (Quorum Acknowledgment) <-
       -> [State Machine (Redis backing)]

Engineering Decisions

  • Consensus: Implemented Raft over Paxos due to its understandability and strong leader-based replication model.
  • Communication: Used gRPC for efficient, strongly-typed remote procedure calls between cluster nodes.
  • Reliability: Persistent log entries ensure nodes can recover state after a crash before rejoining the cluster.

PG-Stats-Monitor

A performance analysis tool for visualizing PostgreSQL internal statistics, lock contention, and query metrics in real-time.

Problem

Debugging database performance issues requires deep visibility into `pg_stat_activity`, table bloat, and cache hit ratios, which are cumbersome to query manually during incidents.

Engineering Decisions

  • Data Extraction: Utilized PostgreSQL internal views (pg_stat_user_tables, pg_stat_statements) with custom CTEs to compute cache hit ratios and sequential scan volumes.
  • Performance: Ensured the monitoring queries themselves are lightweight and non-blocking to avoid exacerbating contention.
