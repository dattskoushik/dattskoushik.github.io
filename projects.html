Incident: Silent Data Corruption in Delta Lake

Post-mortem on identifying and resolving silent data corruption caused by unhandled schema evolution and tombstone messages in a high-throughput Kafka-to-Delta pipeline.

The Failure Mode (Problem)

A downstream reporting dashboard showed a sudden 15% drop in revenue for a specific region. No pipelines failed, and no alerts fired. The root cause was traced to an upstream engineering team deploying a backward-incompatible schema change to a Kafka topic. Null fields (tombstones) intended for GDPR deletes were being incorrectly parsed as valid updates, silently corrupting the Delta Silver layer.

Architecture & Point of Failure

[Upstream DB] -> [Debezium CDC] -> [Kafka Topic]
                                        | (Schema Change + Tombstones)
                                        v
                               [Spark Streaming] -> [Silent Data Loss] -> [Delta Silver]

Forensic Debugging & The Fix

  • Root Cause Analysis: Queried the Delta Lake history log and identified large volumes of null-heavy updates. Inspected raw Kafka payloads to confirm the tombstone messages.
  • Architectural Fix: Refactored the Spark streaming job to use a robust schema wrapper that explicitly handles `null` values and routes tombstone records to a Dead Letter Queue (DLQ) for separate processing.
// The Fix: Explicit Tombstone Handling
val df = spark.readStream...
val processedDf = df
  .withColumn("is_tombstone", col("value").isNull)
  .filter(!col("is_tombstone"))

val dlqDf = df.filter(col("is_tombstone"))

Recovery & Validation

  • Recovery: Performed a targeted backfill using Delta Lake time travel to restore the corrupted partitions.

Incident: Cascading OOM Failures in Daily Aggregations

Post-mortem on debugging and resolving cascading Spark Executor Out-Of-Memory (OOM) errors caused by hidden data skew and inappropriate broadcast join strategies.

The Failure Mode (Problem)

A critical daily aggregation pipeline began failing with `java.lang.OutOfMemoryError` on Spark executors. The pipeline joined a massive fact table (10B+ rows) with a dimension table. The dimension table had unknowingly grown past Spark's `autoBroadcastJoinThreshold`, causing a fallback to a SortMergeJoin, which then failed catastrophically due to severe data skew on a single partition key.

Architecture & Point of Failure

[Fact Table (10B)]                     -> (SortMergeJoin) -> [Executor OOM Crash]
[Dim Table (Skew)] /     ^
                         | (Spill to Disk Failed)

Forensic Debugging & The Fix

  • Root Cause Analysis: Extracted the Spark EXPLAIN plan which confirmed the fallback to SortMergeJoin. Checked the Spark UI and identified a single task taking 10x longer and consuming 90% of memory due to data skew on the 'null' ID.
  • Architectural Fix: Implemented key salting (adding random integers to the skewed key) to evenly distribute the skewed partition across multiple executors, preventing the OOM.
# The Fix: Key Salting for Skew
df = df.withColumn("salt", lit(rand() * 10).cast("int"))
df = df.withColumn("salted_key", concat(col("key"), lit("_"), col("salt")))

Performance Results

  • Optimization: Explicitly hinted a SortMergeJoin with the salted keys, favoring stability over raw speed for this specific pipeline.

*(5) SortMergeJoin [salted_key#123], [salted_key#456], Inner
...

Incident: The N+1 API Rate Limit Disaster

Post-mortem detailing how an orchestrator backfill triggered an unintentional denial-of-service attack on an upstream vendor, leading to an IP ban and a 24-hour pipeline outage.

The Failure Mode (Problem)

During a 3-month historical data backfill, an Airflow DAG was unpaused with `catchup=True`. The DAG dynamically mapped a task to fetch record details per user ID (an N+1 API pattern). Airflow spun up thousands of concurrent tasks, hitting the upstream vendor's API with a massive burst of traffic, instantly exceeding their rate limit and getting our NAT gateway IP permanently banned.

Architecture & Point of Failure

[Airflow Scheduler] -> (Trigger 5000+ Tasks)
                             |
                      [Celery Workers]
                             | (Spike in HTTP Requests)
                             v
                [Upstream Vendor API (IP Banned)]

Forensic Debugging & The Fix

  • Root Cause Analysis: Audited Airflow task logs and identified the N+1 anti-pattern. The lack of concurrency controls meant the backfill executed all mapped tasks simultaneously instead of sequentially.
  • Architectural Fix: Implemented Airflow Pools to strictly limit the concurrency of API-bound tasks to 5 workers. Added a Python `tenacity` retry decorator with exponential backoff and jitter to gracefully handle `429 Too Many Requests` responses.
@retry(
    retry=retry_if_exception_type(RateLimitException),
    wait=wait_exponential(multiplier=1, min=4, max=60),
    stop=stop_after_attempt(5)
)
def fetch_data():
    pass

Optimization Results

  • Optimization: Refactored the ingestion script to use a bulk-export endpoint instead of polling per-record.
